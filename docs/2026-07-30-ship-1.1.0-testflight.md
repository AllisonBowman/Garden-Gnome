# Shipping 1.1.0 to TestFlight — what only you can do

> Everything in this file needs your EAS login, your Apple ID, or a phone in
> your hand. Nothing here can be done from the dev machine — that's why this
> exists instead of a "now go build it."

## Why this matters

`master` is clean and ready: HEAD is `6a29ef1` ("Merge pull request #16 from
AllisonBowman/care-calendar-todos"), the backend suite passes, the mobile
typecheck is clean, the developer-text leak scan is clean, and
`build-precheck.sh production` says **OK to build** (two informational
warnings, both below). `expo.version` in `mobile/app.json` and `APP_VERSION`
in `mobile/src/support.ts` are both `1.1.0` and match. None of that proves the
build works — it proves there's no known reason it *shouldn't*, which is as
far as this machine can take it.

**Correction to what you may have been told about the photo-ID module.**
`mobile/modules/plant-id` is not an unknown quantity the way an earlier draft
of this handoff implied. It has already compiled and run on real hardware —
TestFlight builds 3 through at least 11 (all under the `1.0.0`/`1.0.1` version
strings) shipped it, and a real device test on an **iPhone 17 Pro Max**
already exercised it end to end (`isAvailable()` true, candidates returned).
That test is *why* `docs/plantadvocate-identify-strategy-plan.md` exists: it
found a real, still-unfixed accuracy problem — Vision's on-device image
classifier reduces a photo to a handful of coarse labels (`plant`, `leaf`,
`houseplant`) before Foundation Models ever sees it, so visually similar
species (a Pothos vs. a Heartleaf Philodendron) collide. The planned fix is a
cloud backend (Phase 0, already merged, but inert — the server's
`VISION_BACKEND` defaults to `stub`) with mobile routed to try it first (Phase
1). **Phase 1 has not shipped.** I checked `mobile/src/photoId/identify.ts`
directly: it still only calls the on-device module, and the consent-copy file
(`mobile/src/consent/copy.ts`) says the same thing in its own audit comment,
verified 2026-07-25. So 1.1.0 ships with the *same* on-device-only identify
path, and the *same known* similar-species weakness. That is expected, not a
new bug.

**What genuinely is still open, and only a device run answers:**

1. **This exact commit has never been built.** None of 1.1.0's three feature
   commits touch native code, `eas.json`, or `modules/plant-id` — so there's
   no specific reason to expect a compile regression — but "shouldn't regress"
   and "has been built" are different claims, and only the second is proof.
2. **The hardware floor itself has never specifically been tested.** Every
   device test on record used either an iPhone 17 Pro Max (well above the
   floor) or a non-qualifying iPhone 13 (well below it). Nobody has confirmed
   `isAvailable()` behaves correctly on the actual boundary device — an
   **iPhone 15 Pro / 15 Pro Max on iOS 26**. If you install on exactly that
   hardware, you're answering a question nobody has asked yet.
3. **The three new 1.1.0 features have never run outside the simulator.** The
   care calendar, the Plants to-do list, and the NWS/Open-Meteo weather
   fallback were all verified via `npm run sim`, per
   `~/.claude/projects/.../memory/plantadvocate-sim-run.md`-style runs — never
   on a real device, never through TestFlight's install path, never against
   Sign in with Apple (which the simulator can't exercise honestly at all).

That's the actual shape of the unknown: not "does the headline feature exist"
(it does, and it has real, known limits) but "does *this* build, on *this*
hardware, still behave the way the last one did."

## Warnings `build-precheck.sh production` raised (carry these forward)

- `android package is 'com.allisonbowman.gardengnome'` — old codename, doesn't
  touch an iOS build, pre-existing 1.0.1 cleanup item. Ignore for this build.
- TestFlight lists builds by **version string**, and build numbers are a
  running counter that does **not** reset per version — `1.0.0` alone held
  builds 3, 10, and 11. `1.1.0` will not start at build 1. **Always select by
  build number, never by matching the version string alone.**

## Numbered steps (PowerShell, `C:\Users\14439\Garden-Gnome`)

> PowerShell 5.1 has no `&&`. Chain commands with `;` if you want one line.

### 1. Pull and confirm you're building what you think you're building

```powershell
Set-Location C:\Users\14439\Garden-Gnome
git checkout master
git pull
git log --oneline -3
```

**Look for:** `6a29ef1 Merge pull request #16 from AllisonBowman/care-calendar-todos`
in those three lines — that's the merge carrying all of 1.1.0's code. HEAD
itself will be a docs-only commit sitting on top of it (this file), which
changes the hash but not one byte of the app.

**Write down the hash that `git log --oneline -1` prints.** Call it `$HEAD`.
Step 6 checks that EAS built exactly that, and it's the only thing that
proves the binary came from this tree rather than a stale one. If `6a29ef1`
isn't in the list at all, stop — either the pull didn't land or you're not on
`master`.

### 2. Confirm the working tree is clean

```powershell
git status
```

**Look for:** `nothing to commit, working tree clean`. EAS builds committed
state only — anything uncommitted here is silently excluded from the build,
which produces a build that looks right but isn't. If it's not clean, stop and
work out why before building.

### 3. Confirm the EAS session and registered devices are still what you expect

```powershell
Set-Location C:\Users\14439\Garden-Gnome\mobile
eas whoami
eas device:list --apple-team-id FK6E9XBY6Y
```

**Look for:** `allisonbowman`, matching `owner` in `app.json`. The device list
should show whatever iPhones you actually intend to test on. If a phone you
want to test with isn't listed, register it now — a device added *after* an
internal-distribution build won't be able to install it:

```powershell
eas device:create --apple-team-id FK6E9XBY6Y
```

(Not needed for the TestFlight path below since App Store Connect handles
device authorization differently from ad-hoc internal builds — but it's a
20-second check either way, and cheap insurance if you also want a
development build.)

### 4. Sanity-check the production build profile

```powershell
eas config --platform ios --profile production --non-interactive
```

**Look for:** `"image": "macos-tahoe-26.5-xcode-26.6"` (the Foundation Models
framework needs Xcode 26; a different image can silently strip the feature),
and `"autoIncrement": true`.

### 5. Build

```powershell
eas build --profile production --platform ios
```

Run this in your own terminal — it may prompt about credentials, and
answering "yes, let EAS handle it" is correct unless you have a specific
reason to manage certificates yourself. This runs on Expo's macOS fleet,
~15–30 minutes.

**While it runs:** don't touch the working tree. If you need to do something
else, open a second terminal rather than `cd`-ing away mid-build.

### 6. Confirm the finished build came from the right commit

```powershell
eas build:list --platform ios --limit 1
```

**Look for:** the `Commit` field must match the `$HEAD` hash you wrote down in
step 1. If it doesn't, you built stale code — stop, work out why, and rebuild
before submitting. This check matters more than step 1 did, because it's the
last chance to catch it before the binary goes to Apple.

### 7. Submit to App Store Connect / TestFlight

```powershell
eas submit --platform ios --latest
```

**Look for:** a success message with an Apple Store Connect build ID. Apple
then processes the binary for ~5–10 minutes (can run longer); you get an
email when it's done. It then appears at
https://appstoreconnect.apple.com/apps/6792203800/testflight/ios

### 8. In App Store Connect: identify the right build

Go to the TestFlight tab for the app. **Do not pick by the "1.1.0" label
alone** — if this is truly the first 1.1.0 build you'll only see one, but
confirm the **build number** shown matches what `eas build:list` reported in
step 6, and confirm the **uploaded date** is today, not a stale cached entry.

### 9. Export compliance

`ITSAppUsesNonExemptEncryption` is already `false` in `mobile/app.json`'s
`ios.infoPlist`, so App Store Connect should **not** prompt for an export
compliance question on this upload. **If it does prompt anyway, answer "No"**
(the app doesn't use encryption beyond what's exempt — standard HTTPS/TLS) —
and then tell me it prompted, because that means the `infoPlist` flag isn't
being read the way we think it is.

### 10. Write the "What to Test" notes and add testers

Paste this into the build's "What to Test" field (edit the tester list —
names/emails — to whoever should get this build):

```
PlantAdvocate 1.1.0 — what's new

1. Care calendar: each environment's detail screen now has a month calendar
   scoped to that environment's plants — due dates show as dots, overdue
   items get a banner, and tapping a day opens that day's agenda.

2. Plants to-do list: the Plants tab now opens with a checklist of what's
   overdue or due today across all your plants. Checking a row logs that
   care and reschedules the next one — try it and confirm the calendar
   updates to match.

3. Weather is back. Apple's weather service has a provisioning problem on
   Apple's side (ticket filed, not something we can fix in the app), so
   weather now comes from the National Weather Service, with a global
   fallback for non-US locations. Expected side effect: no UV index and no
   "hours of daylight" line will show for any environment. That's not a bug
   — please don't report it — it's a real gap in what the free weather
   source provides versus Apple's.

Please test on a real device, not just install-and-glance:
- Add a plant via photo (the identify button, if you see it, requires an
  iPhone 15 Pro or newer on iOS 26 — on any other phone the button should
  simply not appear, which is correct).
- Sign in with Apple (only works on-device, never in a simulator).
- Check off a couple of care-log items and watch the calendar respond.
```

### 11. Install and test on device(s)

Install the TestFlight build (internal testers get it as soon as processing
finishes — no App Review needed for internal testing).

**11a. Check the phone(s) you're installing on, don't assume:**
Settings → General → About → Model Name, plus the iOS version. Note this down
per phone — you'll need it for the report back.

**11b. If a phone is an iPhone 15 Pro / 15 Pro Max or newer, on iOS 26:**
- Add Plant → the photo-identify button should be **visible**.
- Photograph 4–5 distinctive plants you can identify yourself.
- Note whether it offers candidates, whether they're real catalog species,
  and whether the right one shows up. **Expect it to sometimes confuse
  visually similar species (e.g., different Philodendron look-alikes) — that
  is the known, documented limitation, not a new failure.** What's worth
  flagging is anything *beyond* that: crashes, the button appearing then
  erroring instead of just returning "no match," or garbage/non-plant output.

**11c. If no phone on hand qualifies:**
- Add Plant → the photo-identify button should be **absent**, not greyed out,
  not erroring — just not there. Confirm manual species search still works.
  This is the fallback path most real users will actually hit; confirming it
  matters just as much as 11b.

**11d. Weather:** open an environment with a location set. Confirm a forecast
renders at all (that's the actual fix), and confirm the credit line names
whichever provider answered (NWS or Open-Meteo — check
`docs/2026-07-30-weatherkit-401-closed.md` if you want the detail). Confirm
there's no UV or daylight line, and that its absence looks intentional
(nothing blank/broken-looking where it would have been) rather than like a
missing element.

**11e. Care calendar / to-do list:** open an environment's detail screen,
confirm the month grid, due dots, and overdue banner. Tap a day, confirm the
agenda. Then go to the Plants tab, check off an overdue item, and confirm it
disappears from the to-do list and the due date moves in the calendar.

**11f. Sign in with Apple:** from a signed-out state, confirm the flow
completes on-device. (This has never been verified outside a simulator, where
it can't be honestly tested at all.)

## Results table — every outcome, and what it means

| What you see | What it means | What to do |
|---|---|---|
| **Build succeeds, commit matches** | The module and the rest of 1.1.0 compiled clean on this exact commit. Genuinely useful confirmation, even though it was expected. | Continue to submit (step 7). |
| **Build fails in "Run fastlane" / a Swift compile phase, error names `PlantIdModule.swift` or `FoundationModels`** | A real regression — something changed in the SDK/toolchain that broke a module that has compiled successfully many times before. Worth taking seriously precisely because it *used* to work. | **Send me the full log URL, don't try to patch it live.** This is a genuinely new problem, not the known accuracy limitation. |
| **Build fails on credentials / provisioning** | Signing setup, not the module or the app code. `appleTeamId` is pinned in `app.json` (fixed 2026-07-25 for a related simulator issue), so this is less likely than it used to be, but EAS-managed credentials can still expire or need re-sync. | Re-run and let EAS manage credentials when prompted. If it fails twice the same way, send me the error text. |
| **Submit succeeds, but App Store Connect rejects on export compliance** | The `ITSAppUsesNonExemptEncryption: false` flag isn't being honored, or something in a new dependency (e.g. an image/crypto library from the care-calendar work) added an undeclared encryption usage. | Answer the compliance question directly in ASC (almost certainly "No" is still correct), then tell me it prompted — that's new information worth recording regardless of how you answered it. |
| **Submit succeeds, but TestFlight processing gets stuck ("Processing" for well over an hour)** | Usually an icon/asset validation issue, a missing required Info.plist key, or an ASC-side outage — rarely the app code itself. | Check for an email from Apple first (they usually explain why). If there's no email after ~2 hours, check https://developer.apple.com/system-status/ before assuming it's our bug. |
| **Build and submit both succeed, but the app crashes on launch** | Something broke that neither `tsc` nor pytest can catch (a native init crash, a missing entitlement). This is a genuinely new class of failure regardless of cause. | Screenshot/copy the crash if one appears, note the exact phone + iOS version, and send both — do not attempt a workaround build yet. |
| **Everything installs and runs, but the identify button never appears on a qualifying 15-Pro-or-newer/iOS-26 phone** | Either that phone's Apple Intelligence isn't actually enabled (Settings → Apple Intelligence & Siri), or `isAvailable()` has a real bug at the hardware floor — a new finding, since only above-floor hardware has been tested before. | Check Apple Intelligence is toggled on in Settings first. If it's on and the button still doesn't show, that's worth reporting as a real bug. |

## What to report back

In roughly this order of how much it changes the next move:

1. **Did the build succeed, and did the commit in `eas build:list` match the
   `$HEAD` you noted in step 1?** If not, the full log URL.
2. **Did submit + TestFlight processing complete, and what build number did
   it land as?** (Needed so future installs pick the right one.)
3. **Which phone(s) did you test on — exact model and iOS version** (from
   Settings → General → About), and did each qualify for Apple Intelligence?
4. **On a qualifying phone:** was the identify button visible, and for the
   4–5 photos you tried, what came back? Specifically flag anything beyond
   the known similar-species confusion (crashes, dead button, junk output).
5. **On a non-qualifying phone (or none available):** confirm the button was
   absent and manual search worked.
6. **Weather:** did a forecast render, which provider's credit showed, and
   did the missing UV/daylight look intentional rather than broken?
7. **Care calendar + to-do list:** did checking off an item update both
   surfaces correctly?
8. **Sign in with Apple:** did it complete on-device?
9. **Anything else that looked wrong** that isn't covered above — trust your
   own eye on how the app is supposed to feel; you know that better than this
   handoff does.
